# M2 walkthrough: Upload and distribute

## 1. The big picture

M2 lets a person pick up to 100 files, send them to up to 20 team folders in one action, and see the documents arrive. It is the biggest milestone, because a file now travels through five places before it lands in a folder, and every place can fail.

The path is: **browser → Object Store (S3) → Upload Events Lambda with ClamAV → DocBeam API → queues → Fan-out and Delivery Lambdas → Document Platform → Platform File Store.**

Three ideas hold it together:

- **Upload once, deliver many times.** A file goes to S3 one time. Delivery then copies it to each folder. So 100 files to 20 folders is 100 uploads and 2,000 deliveries.
- **Nothing unchecked moves on.** The browser fingerprints each file (SHA-256). S3 refuses bytes that do not match it. ClamAV scans every file. Delivery checks the fingerprint again and the platform checks it a third time.
- **Every step can be repeated safely.** Queues deliver a message more than once, a browser retries, a worker crashes. Each step is built so that doing it twice changes nothing.

M2 adds no new database. It uses the DocBeam database from M1 for files, jobs, tasks and the audit trail. A **job** is one Send. A **task** is one file going to one folder.

## 2. One upload and one send, start to finish

Anantim picks `consent.pdf` (3 MB) and `brochure.pdf` (120 MB) and ticks three folders.

**Step 1. The browser reads and fingerprints the files.** A Web Worker computes each file's SHA-256 in 16 MiB slices, so the page stays responsive. The page also checks the allow-list (PDF, Office, images), the size (1 byte to 1 GiB) and the limit of 100 files.
- Why: the fingerprint is the thread that ties every later check together (D-M2-7).
- Code: `web/src/upload/hashing.ts`, `hash.worker.ts`, `web/src/distribute/files.ts`.
- Test: `hashing.test.ts`, `files.test.ts`.

**Step 2. The page asks for upload links.** `POST /uploads` returns, for a small file, a **presigned POST form**. The SHA-256 and the size are signed into it, so S3 itself refuses other bytes. For the 120 MB file (over 100 MiB) the page starts a **multipart upload** and gets one link per 16 MiB part (8 parts), each with its own fingerprint. The API also writes a `files` row (state `pending`).
- Why: the browser sends the bytes straight to S3, so the API never carries large files.
- Code: `services/docbeam-api/src/routes/uploads.ts`.
- Test: `uploads.test.ts`. On dev, a swapped body gets `400 BadDigest`.
- AWS: S3 → `docbeam-dev-object-store-<account id>` → `staging/`.

**Step 3. The page uploads, 4 files at a time.** It refreshes links after 13 minutes (they last 15), resumes a multipart file from the parts already stored, and retries a dropped connection after 2, 4 and 8 seconds. When all parts are in, `complete` joins them.
- Code: `web/src/upload/manager.ts`, `browser-transport.ts`. The bucket's CORS rule lets the page's own address make these calls.

**Step 4. S3 tells the Upload Events queue, and the Lambda wakes up.** For every new object under `staging/`, S3 puts a message on the Upload Events queue. The **Upload Events Lambda** (a container image that carries the ClamAV scanner) reads the object's size and checksum and compares them with the `files` row. Then it streams the file through ClamAV and works out the SHA-256 in the same pass.
- A clean file gets the S3 tag `scan-status=clean` **first**, and then the row is updated (`uploaded_at`, `scan_status = clean`) in one conditional update. A repeat of the event changes nothing.
- An infected file (the EICAR test file, for example) is deleted, the row is marked `infected` and a `file.refused` audit event is written.
- Why: the bucket policy lets nobody read a staged file unless it carries the clean tag (ADR-016). The tag is the gate.
- Code: `workers/upload-events/src/process.ts`, `scanner.ts`. Test: `upload-events.test.ts` ("EICAR is refused as infected by the real ClamAV").
- AWS: Lambda `docbeam-dev-upload-events`, Monitor → Logs (`file confirmed clean` or `file refused`); SQS `docbeam-dev-upload-events`.

**Step 5. The page polls and shows the state.** `GET /files?ids=` every 2 seconds. The file goes `Checking for malware`, then `Verified` or `Refused`. Send turns on only when every file is Verified.

**Step 6. Send.** `POST /jobs` with an `Idempotency-Key`. The API checks the batch limits, that the files are the caller's, not older than 24 hours, still match their fingerprints and are clean, then asks the platform (with one call) whether every destination exists and the caller belongs to its team. In **one database transaction** it inserts the job, marks the files as taken, inserts one pending task per file per folder, and writes the `job.submitted` audit event. Only after the commit does it put one message, `{jobId}`, on the Job queue.
- Why: if the message is sent and the commit fails, work would run for a job that does not exist. If the message is lost after the commit, the **Sweeper** re-sends it two minutes later.
- Code: `routes/jobs.ts`. Test: `jobs.test.ts` (13 tests, including 100 files × 20 folders in one request).
- AWS: SQS `docbeam-dev-job`.

**Step 7. Fan-out.** The Fan-out Lambda reads the job message and puts one message per task on the Task queue (`{taskId}` only, never a token), ten at a time.

**Step 8. Delivery, up to 50 at once.** Each Delivery Lambda run takes one task, **claims** it (`pending → in_progress`), checks the object in S3 still has the declared checksum, gets a service token and streams the file to the platform's `POST /documents`. The platform checks the file type by its first bytes, recomputes the SHA-256, uploads to the Platform File Store in 5 MB parts and inserts the document (one document per task, however many times it is asked).
- A `201`, or `200` for a repeat, completes the task. A "not a member", "destination gone" or "checksum" answer fails it for good. Anything else (a 5xx, a timeout) puts it back to pending and waits 30 s, 2, 5 and 10 minutes before trying again.
- Why: a short outage of the platform should be ridden out, not turned into failures.
- Code: `workers/delivery/src/deliver.ts`, `classify.ts`; `services/platform/src/routes/documents.ts`.
- AWS: Lambda `docbeam-dev-delivery` logs (`task delivered`); ECS → `docbeam-dev-platform` → Logs; S3 → `docbeam-dev-platform-files-<account id>` → `documents/`.

**Step 9. The last task closes the job.** Every final status is written in one transaction that first **locks the job row**. So if the last two tasks finish at the same moment, the second sees the first and closes the job, exactly once.

**Step 10. A task that keeps failing ends in the DLQ.** After five tries SQS moves it to the Task DLQ. The **DLQ Consumer** marks it `RETRIES_EXHAUSTED` with its last error, closes the job if nothing is open, and the alarm for that DLQ can raise an email (SNS).
- AWS: SQS `docbeam-dev-task-dlq` (should be 0); CloudWatch → Alarms (four, all `OK`).

## 3. The parts where a mistake would cause real harm

1. **Checksums, end to end.** A wrong fingerprint check would let a corrupted or swapped file into a clinical trial folder. The check happens in four places: S3 (signed policy or per-part checksum), the Upload Events Lambda (stored size and checksum, plus its own SHA-256 during the scan), Delivery (checksum of the staged object) and the platform (recomputes while streaming). Tests: `uploads.test.ts`, `upload-events.test.ts` ("refuses bytes that differ from the declared SHA-256"), `delivery.test.ts` ("fails CHECKSUM_MISMATCH…"). On dev: `BadDigest`, and Delivery refuses a task whose object has no checksum (D-M2-15).
2. **Doing a step twice.** A second job, a second document or a second audit line for one click would be a real error in a trial record. Guards: the `Idempotency-Key` (a repeat returns the same job; two at once make one), the task claim, `ON CONFLICT (source_task_id)` in the platform, conditional updates in Upload Events, and the job row lock. Tests: "returns the same job for a repeated key", "gives one job to two requests with the same key that run at the same time", "stores one document and writes one audit event when the same message arrives twice", "closes the job exactly once when its last two tasks finish together".
3. **Retries and the DLQ.** A task must never be lost and never stuck. Tests: "puts a task back to pending when the platform is down, and finishes it when it returns", the six DLQ Consumer tests, the Sweeper tests. On dev: the platform was stopped for five minutes with 862 tasks waiting, and all 1,400 tasks were delivered exactly once afterwards. Twice, tasks reached the Task DLQ and were marked `retries exhausted`, and the job closed.
4. **Scanning.** Nothing unscanned may be handed to anyone. The clean tag gates every read of a staged file (bucket policy), the file is deleted if infected, and a file that could not be checked is shown as such. Tests: the EICAR test with the real ClamAV; on dev the EICAR file was refused with `reason MALWARE`.
5. **The platform's ingest cap.** Found on dev, not in the design: fifty large deliveries at once ran the platform out of memory and it restarted over and over. The platform now takes six ingests at once, holds one 5 MB part per upload, has 1 vCPU and 2 GB, and answers `503 PLATFORM_BUSY` to a request that has waited 30 seconds (Delivery then tries later). Tests: `ingest-limiter.test.ts`; on dev the 50-delivery run completed with peak memory 13.9% and 32 busy-retries (D-M2-22).

## 4. What can safely be ignored for now

- Most of `web/src/components` apart from `Distribute.tsx`, `AddFiles.tsx`, `Review.tsx` and `SendBar.tsx`: layout and styling.
- The Terraform modules `lambda`, `sqs`, `scheduler` and `alarms`: read the variables, not the resources. They follow one pattern.
- The local stand-ins (`worker-runtime`, `ws-local`): they only run the same handlers on a laptop.
- Pushes to the page (`push.ts`): the code exists but sends nothing on AWS until M3 builds the WebSocket API.

## 5. Questions a reviewer might ask

1. **Why does the browser upload straight to S3?** So large files never pass through the API, and S3 can enforce the fingerprint itself.
2. **What if the browser closes mid-upload?** The files are lost from the page (the leave warning asks first). Files already uploaded but not sent are deleted by the Sweeper after 24 hours.
3. **What stops someone reading an unscanned file?** The bucket policy denies reads unless the object has the clean tag, except for the Upload Events role that sets it.
4. **What happens if the Job queue message is lost?** The Sweeper finds jobs with no fan-out two minutes after they were queued and sends the message again. A second fan-out is harmless.
5. **Can one file reach one folder twice?** No. The task is claimed once, the platform has a unique key on the task, and a repeat returns the first document.
6. **What if the platform is down?** Submit answers `503` and the page retries with the same key. Deliveries wait and retry on a schedule, and about 17 minutes of retries are allowed before a task fails for good.
7. **Why a limit of six ingests at once?** One platform task has finite CPU and memory. The limit keeps work bounded however fast Delivery sends. It is sized for this stand-in platform; the real platform's capacity is the client's to confirm.
8. **Why is Delivery capped at 50?** To stay under the database's connections (each copy opens one). Extra messages wait in the queue instead of being refused.
9. **Why did dev show a failure the tests did not?** LocalStack does not enforce a signed checksum, does not limit memory, and delivers faster than real AWS. The dev run found the Lambda image format (Lambda refuses an image that carries a build attestation) and the platform memory problem, and showed that even the admin user cannot read a staged object (which is the policy working as designed).
10. **What is left for M3?** Showing a job live: the status endpoints, the WebSocket API and the Status page. Delivery already writes everything M3 will read.

## 6. Words used

- **Object Store:** the S3 bucket where uploads wait (`staging/`) until delivered.
- **Platform File Store:** the S3 bucket where delivered documents live.
- **Presigned POST / multipart:** a time-limited S3 upload permission for the browser; multipart splits a big file into 16 MiB parts.
- **SHA-256:** a fingerprint of a file's bytes.
- **Job, task:** one Send; one file going to one folder.
- **Idempotency-Key:** a random value the page sends with Send, so a repeat is recognised.
- **Claim:** moving a task to `in_progress` so only one worker handles it at a time.
- **DLQ (dead-letter queue):** where a message goes after too many failures.
- **ClamAV / EICAR:** the malware scanner; the harmless standard test file every scanner must flag.
- **Fan-out:** turning one job message into one message per task.
- **Sweeper:** the scheduled Lambda that re-sends lost job messages and deletes stale uploads.
- **Draining:** letting a stopping server finish what it has started (120 seconds here).
