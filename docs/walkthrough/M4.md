# M4 walkthrough: Download a file

## 1. The big picture

After M3, a person could see that a file was delivered but could not open it. M4 adds the last flow: on each delivered file on the Status page there is an eye (**Preview**) and an arrow (**Download**). Preview shows the file in the page. Download saves it under its original name.

Three ideas hold it together:

- **The server decides, then hands out a short link.** The browser never gets a file from DocBeam. It asks the DocBeam API for a link. The API checks who is asking and, if that is allowed, signs a link for that one file that works for 2 minutes. The browser then fetches the bytes straight from the Object Store (S3). File contents never pass through our servers.
- **"Not allowed" and "does not exist" look the same.** Anyone who is not the sender, and is not in a team the file was delivered to, gets 404 with the same message as for a random id. The API never says that a file exists, and never says that it has expired, to someone who may not see it.
- **The page shows other people's files safely.** PDFs and images open from the link in the browser's own viewer. DOCX and XLSX are turned into plain HTML in the browser and shown in an iframe with `sandbox=""` (no scripts, no same origin), so a file someone else sent cannot run code in the page. This viewer was built in M2 for files before Send. M4 reuses it.

M4 adds no table, no queue and no Lambda. It adds one API route, one API Gateway route and some web code.

## 2. One request, start to finish

Raj (in Cardio) opens a distribution that Priya sent to Cardio and Oncology, and clicks the eye on `consent.pdf`.

**Step 1. The page asks for a link.** `useFileLink` (`web/src/tracking/useFileLink.ts`) calls `POST /api/files/<file id>/downloads` with `{"mode":"preview"}` through `apiFetch`, which adds Raj's access token.
- Why: a new link is made on every click. Nothing is cached, so a link is never older than the click.

**Step 2. The gateway checks the token.** API Gateway's JWT authorizer rejects a call with no token or a bad one (401) before it reaches our network. The route is listed one by one in `infra/envs/dev/services.tf`.

**Step 3. The API looks the file up.** `routes/downloads.ts` reads the file, its job and the job's sender in one query. A file with no job, or a missing id, or one that is not scanned clean, is a 404.

**Step 4. The API decides who may have it.** The sender is allowed. For anyone else the API asks the Document Platform for Raj's teams (`platform.userTeams`, cached for 60 seconds) and looks for a **completed** delivery of this file to one of them. The pure function `decideDownload` holds the rule and its order: not found, then not allowed (both 404), then expired (410). Raj is in Cardio and the Cardio delivery completed, so he passes.
- Why completed, not just "a task exists": a delivery that is still waiting or failed has not put the file in Raj's folder yet.

**Step 5. The API signs the link.** `ObjectStore.presignGet` (`services/docbeam-api/src/s3.ts`) signs a GET for that one object in this process, with no call to AWS. It sets `response-content-disposition` and, for a preview, `response-content-type`. A preview is `inline` with the stored type. A download is `attachment; filename="…"; filename*=UTF-8''…` with the original name. Quotes, slashes, semicolons and line breaks are taken out of the plain name, so a hostile file name cannot add a header or break out of the quotes.

**Step 6. The API writes the audit row.** `download.issued` with the job, the actor's name and email, the file, the mode and the team (Cardio). Because Raj is not the sender, the row has a team, so the other Cardio people and the sender can see it. A sender's own download has no team, so only the sender sees it.
- Why this order: the row is written after the link is signed but before the reply, so a failed write fails the request. There is never a link without a record.

**Step 7. The page shows the file.** The reply is `{url, expiresAt, fileName, contentType, sizeBytes}`. The dialog (`Preview.tsx`) shows a PDF in an iframe and an image in an `img`, both straight from the link. For a DOCX or XLSX it fetches the bytes from the link (S3's CORS rule allows GET from the site), up to 50 MB, and renders them into the sandboxed iframe.

**Step 8. Download is the same call with `mode: download`.** The page clicks a hidden link to the URL. The `attachment` header makes the browser save it, so the page stays where it is. A blue bar counts down from 2:00. At 0:00 it turns red and says the link has expired and storage now refuses it. That is true: S3 answers 403 `Request has expired` (checked on dev).

What to look at in the AWS Console (Sydney, read only): S3 → the Object Store → Permissions (the bucket policy keeps `DenyReadUnlessScannedClean` and nothing unscanned can be read); API Gateway → `docbeam-dev-api` → Routes (`POST /files/{fileId}/downloads`, JWT); CloudWatch → `/docbeam/docbeam-dev/docbeam-api` (request lines, no signed URLs).

## 3. The parts where a mistake would cause real harm

**1. Who gets a link** (`decideDownload`). A bug here shows clinical documents to the wrong team. Tests: `downloads.test.ts` (11 unit cases: sender, delivered team, not-yet-delivered, outsider, not clean, expired, bad mode) and `tests/integration/downloads.test.ts` (the same through the real route, with Priya, Raj and Sam, and the bytes of a real object). On dev: curl checks 3 and 4, and the browser runs as Raj and Sam.

**2. What the 404 reveals.** If an outsider got 410 for an old file, or a different body for a real file, they would learn it exists. The order in `decideDownload` and the shared `notFound` message prevent that. Tests: "gives an outsider 404, never 410, for an expired file" and "gives 404 to someone in neither team, the same answer as for a file that does not exist" (same body).

**3. The link itself** (`presignGet`, `contentDisposition`). It must name one object, last 2 minutes, and carry a safe header. Tests: `s3.test.ts` (120 s, one key, header text for quotes, line breaks, non-ASCII). On dev: 130 seconds later both a download and a preview link got 403, and the bucket with no link got 403.

**4. The viewer for other people's files** (`Preview.tsx`). DOCX and XLSX must stay in the empty sandbox. Tests: `Preview.test.tsx` (sandbox is `""`, no `src`, cells escaped) and the Playwright runs, which read the sandbox attribute and the text inside the frame.

## 4. What can be ignored

- The CSS of the banner and the dialog.
- `links.ts` text strings (they are copy from the mockup, with one test).
- The Playwright dev config (`playwright.dev.config.ts`) beyond knowing that `npm run test:e2e:dev` runs the same specs on dev with a password from Secrets Manager.
- The old off state of the buttons ("Preview and download arrive in the next milestone"): gone.

## 5. Questions a reviewer might ask

1. **Why not send the file through the API?** It would make the API scale with bandwidth and hold a connection per 1 GB download. A signed link keeps the bytes between S3 and the browser (ADR-002).
2. **Why 2 minutes?** A link is used once, at the click. Short expiry limits what a leaked link is worth (ADR-004).
3. **Can someone share a link?** Yes, for up to 2 minutes, for that one file. That is the accepted risk in the design.
4. **Why is a preview logged like a download?** A preview hands out the same bytes. The audit trail must show it.
5. **What if the file is older than 33 days?** The Object Store has deleted it. The API answers 410 FILE_EXPIRED to people who are allowed, and the row says the delivered copy is still in the team folder.
6. **Why does Raj not see Priya's own downloads?** Her downloads have no team, so only she sees them. His have a team, so she and his teammates see them.
7. **Why does the 201 carry `fileName`, `contentType` and `sizeBytes`?** The viewer needs the type to pick PDF, image or office view, and it shows the size. The task rows only have the name (D-M4-1).
8. **Why is a pending delivery a 404 and not a 409?** Anything other than a clear yes must not reveal the file.
9. **Can the unscanned file be previewed?** No. The route refuses it and the bucket policy denies reads without the clean tag.
10. **How was link expiry tested if LocalStack ignores it?** On dev, with curl: the same two links worked at once and returned 403 after 130 seconds.

## 6. Glossary

- **Presigned link:** an S3 address with a signature and an expiry in the query. Whoever holds it can do that one operation until it expires.
- **Content-Disposition:** the response header that tells the browser to save a file (`attachment`) or show it (`inline`).
- **Sandboxed iframe:** a frame with `sandbox=""`, which blocks scripts, forms and access to the page's data.
- **Delivered:** a task whose status is `completed`: the document is in the team's folder.
- **410 FILE_EXPIRED:** "this existed, but it is gone". Used only for callers who may see the file.
- **Audit event:** an append-only record. `download.issued` has `detail.mode` `download` or `preview`.
