# M0 walkthrough: Foundations

Read this to explain what M0 built and why. It has no features a user can see. It builds the ground the other milestones stand on.

## 1. The big picture

M0 builds the empty frame of DocBeam: the repository, the local stack, the AWS infrastructure and the pipelines. Three services and six workers exist as skeletons that start, answer `/health` or log a line, and do nothing else yet. The same code runs on a laptop (Docker Compose and LocalStack) and on AWS (Terraform). Every later milestone adds behaviour to a part that already starts, deploys and has tests. The money and safety rules are set here too: no secrets in git, dev that can be destroyed and re-created in one command, and prod that nobody can reach by accident.

## 2. One request, start to finish

M0 has no user request. It has three actions a developer does. Follow each one.

### A. `docker compose up`: the services start

1. **Postgres starts and creates the databases.**
   - *Why:* each service owns its own database and nobody else may read it (ADR-009). Tables are owned by a role that cannot log in, so the audit trail can be append-only (D-G8).
   - *Code:* `docker/postgres/10-bootstrap.sh` calls `docker/db-bootstrap/bootstrap.sh`, the same script AWS runs. It creates `auth_db`, `platform_db`, `docbeam_db`, three `*_owner` roles (no login) and three `*_app` roles (login).
   - *AWS:* RDS console, instance `docbeam-dev-postgres`. The same script ran as an ECS task: CloudWatch Logs, group `/docbeam/docbeam-dev/db-bootstrap`, lines `database ready`.
2. **LocalStack starts and creates buckets and queues.**
   - *Why:* S3 and SQS must behave like AWS so the same code runs in both (TDD Step 0.1). Queue settings match the design: 3 tries for jobs, 5 for tasks and uploads, then a dead-letter queue (ADR-005).
   - *Code:* `docker/localstack/init/ready.d/init.sh`. The `staging/` upload event goes to the Upload Events queue (ADR-016).
   - *AWS:* the real buckets are made by `infra/modules/s3/main.tf`. Console: S3, three `docbeam-dev-*` buckets.
3. **Each service runs its migrations, then starts.**
   - *Why:* a service's schema changes ship with the service (ADR-009). Migrations connect as the login user, then `SET ROLE <name>_owner` (D-M0-2).
   - *Code:* `services/<name>/src/migrate.ts`, then `src/server.ts`. `/health` is in `src/app.ts`. It does not touch the database, so a database blip does not take a service out of the load balancer.
   - *AWS:* ECS console, cluster `docbeam-dev-cluster`. Services arrive in M1.
4. **The `workers` container polls the queues and calls the handlers.**
   - *Why:* the Lambda code must run locally unchanged (ADR-011). `packages/worker-runtime` does what the Lambda SQS trigger does: a batch, delete the successes, leave the failures.
   - *Code:* `packages/worker-runtime/src/poller.ts` (`pollQueue`), `src/batch.ts` (`runBatch`). The handlers are in `workers/*/src/index.ts`.
   - *AWS:* Lambda console. The functions arrive in M2.
5. **`ws-local` stands in for the WebSocket API.**
   - *Code:* `packages/worker-runtime/src/ws-local.ts` (`startWsLocal`). It calls the WS handler and offers `POST /@connections/{id}` like API Gateway, returning 410 when the connection is gone.

### B. A merge to `main`: what CI does

1. **On a pull request, `ci.yml` runs** lint, typecheck, unit tests, build, then the integration tests on Compose, then gitleaks over the whole history.
2. **A service workflow runs only if its paths changed** (`auth.yml`, `platform.yml`, `docbeam-api.yml`, `web.yml`, `workers.yml`, `upload-events-image.yml`). The three service workflows share `_service.yml`.
3. **The deploy jobs are skipped** unless the switch variable is `true`: `ECS_DEPLOY_ENABLED`, `LAMBDA_DEPLOY_ENABLED`, `INFRA_APPLY_ENABLED` (D-G4).
4. **Prod never runs on a merge.** It runs only from a manual run on `main` with `deploy-prod` typed (D-G3).
   - *Code:* the `if:` lines of the `deploy-prod` and `apply-prod` jobs in `.github/workflows/`.
   - *AWS:* nothing changes. Look in GitHub: Actions, Environments.
5. **Daily at 03:17 UTC** `upload-events-image.yml` rebuilds the scanner image so virus definitions stay fresh (ADR-016).

### C. `terraform apply`: what gets created

1. **State is stored in the state bucket** `docbeam-tfstate-346208529537` with a lock file (ADR-012). *Code:* `bootstrap/create-state-backend.sh`, `backend "s3"` in `infra/envs/dev/main.tf`.
2. **`infra/envs/dev` only calls modules** with dev values. `infra/envs/prod` does the same with prod values. *Why:* one set of modules, so dev proves what prod runs.
3. **The modules create:** `network` (VPC, two zones, one NAT in dev, an S3 gateway endpoint), `rds` (PostgreSQL 16, encrypted, three role secrets), `s3` (Object Store, Platform File Store, web bucket), `cloudfront` (the web app), `ecr` (five repositories), `ecs-cluster` (cluster and the bootstrap task), `secrets` (service client secrets and an empty signing-key secret, D-M0-1).
   - *AWS:* console, Sydney: VPC, RDS, S3, CloudFront, ECR, ECS, Secrets Manager. Eighty-six resources in dev.
4. **RDS Proxy is off in dev** (D-M0-6). The Free plan blocks it. Lambdas will connect to the instance directly. `rds` output `lambda_db_host` is the only thing that differs.
5. **Dev can be destroyed and re-created** (D-M0-4): secrets have no recovery window, buckets and repositories are force-deleted. Proven: destroy, apply again, no name conflicts.

## 3. The parts that matter most

**1. Secrets must never reach git or a log.**
- *Wrong:* a key or password in a file, a commit or the chat.
- *Prevented by:* passwords are made by `random_password` and stored in Secrets Manager (`infra/modules/rds`, `infra/modules/secrets`). The RDS master password is managed by RDS. The signing key secret is created empty, so the key never enters Terraform state (D-M0-1). `.env` is git-ignored and `.env.example` holds only local defaults. gitleaks runs in CI.
- *Proof:* the `gitleaks` job in `ci.yml`; `aws secretsmanager describe-secret` on the signing key shows no versions.

**2. The audit trail must be append-only.**
- *Wrong:* the service's login role owns the tables, so any bug could edit history.
- *Prevented by:* the owner role cannot log in and owns the tables; the app role only gets table rights through default privileges (D-G8, D-M0-2). `bootstrap.sh` never makes the app role a member of the owner.
- *Proof:* `tests/integration/postgres.test.ts`: "has six roles", "does not let an app role create tables", "lets each app role into its own database only".

**3. An unscanned file must never be handed out.**
- *Wrong:* a role reads an object that was not scanned clean, or the wrong role writes to the bucket.
- *Prevented by:* the Object Store policy denies object access to every role not in the allow-list, and denies `GetObject` unless the object is tagged `scan-status=clean` (ADR-016). The Platform File Store denies `DeleteObjectVersion` in prod. See `infra/modules/s3/main.tf`.
- *Proof:* on dev, an upload by the admin user returns `AccessDenied ... explicit deny in a resource-based policy` (`M0-RESULTS.md`). Read-after-clean is proved in M2.

**4. Cost and prod must stay under control.**
- *Wrong:* dev left running by mistake, a merge that applies to prod, or Lambdas using up the database's connections.
- *Prevented by:* the switch variables above; prod only by hand from `main` (D-G3); dev settings that make destroy clean (D-M0-4); a connection budget of 79 of 100 (D-M0-6).
- *Proof:* `packages/shared/src/db.test.ts` fails if the budget goes over 80%. The destroy and re-create run in `M0-RESULTS.md`.

## 4. What you can safely ignore for now

- Config files: `tsconfig*.json`, `eslint.config.js`, `vitest*.ts`, `.dockerignore`, `package-lock.json`.
- The Dockerfiles' layer order and the esbuild banner line in each worker's `package.json`.
- The Terraform plumbing: route tables, security group rules, IAM trust policies and the `random` provider.
- `web/`: a placeholder page until M1. Only the Vite `/api` proxy matters later (D-G5).
- The Drizzle files (`schema.ts`, `drizzle.config.ts`): empty until M1.
- The `esbuild` warnings from `npm audit`: they are inside drizzle-kit, a build-time tool.

## 5. Things you should be able to answer

1. **Why three databases on one instance?** Each service owns its data, and a cross-service join is impossible. One instance keeps cost low (ADR-009). See `docker/db-bootstrap/bootstrap.sh`.
2. **Why can't the app role create or delete tables?** So the audit trail stays append-only (D-G8). See `postgres.test.ts`.
3. **Why does dev have no RDS Proxy?** The Free plan blocks it. The code does not depend on it, and M5 runs with it on (D-M0-6). See `infra/modules/rds/main.tf`.
4. **How do you know dev will not run out of database connections?** Every Lambda opens at most one; the worst case is 79 of 100. See `packages/shared/src/db.ts`.
5. **How is prod protected from an accidental deploy?** Only a manual run from `main` with `deploy-prod` typed, in the `prod` environment (D-G3). See `.github/workflows/infra.yml`.
6. **Why is the signing-key secret empty?** So the private key never enters Terraform state (D-M0-1). See `infra/modules/secrets/main.tf`.
7. **Why does dev keep one NAT gateway and prod two?** Cost in dev; one per zone in prod so a zone failure does not cut egress. See `infra/modules/network/main.tf`.
8. **Why is LocalStack pinned to 4.14?** The newest image needs an auth token (D-M0-5). See `docker-compose.yml`.
9. **How do the workers run locally?** `worker-runtime` polls the queues and calls the same handler, like the Lambda trigger. See `packages/worker-runtime/src/poller.ts`.
10. **What stops a destroy from failing or a re-create from clashing?** Force-delete settings and a 0-day secret window in dev only (D-M0-4). See `infra/envs/dev/main.tf`.

## 6. Words used

- **ADR / D-xx:** a recorded design decision (`docs/design/04-adrs.md`, `docs/DECISIONS.md`).
- **Terraform:** a tool that creates AWS resources from code.
- **Module:** a reusable Terraform package. `envs/dev` and `envs/prod` only call modules.
- **State bucket:** the S3 bucket where Terraform remembers what it made.
- **Compose:** Docker's way to run many containers together.
- **LocalStack:** a local imitation of S3 and SQS.
- **Lambda:** a function AWS runs for one event, billed per use.
- **ECS Fargate:** AWS runs a container for you, with no server to manage.
- **SQS / DLQ:** a queue of messages / the queue where failed messages end up.
- **Visibility timeout:** how long a taken message stays hidden before it comes back.
- **RDS / RDS Proxy:** AWS's managed PostgreSQL / a pool that shares its connections.
- **Owner role / app role:** the role that owns tables and cannot log in / the role a service uses at run time.
- **Migration:** a versioned change to a database's tables.
- **Secrets Manager:** AWS's safe place for passwords and keys.
- **JWT / JWKS:** a signed login token / the public keys that check it.
- **ClamAV:** the malware scanner inside the Upload Events image.
- **CloudFront:** AWS's content delivery network, in front of the web app.
- **NAT gateway:** lets private servers reach the internet and costs money every hour.
- **gitleaks:** a scanner that finds secrets in git history.
- **Switch variable:** a GitHub variable (`ECS_DEPLOY_ENABLED`, `LAMBDA_DEPLOY_ENABLED`, `INFRA_APPLY_ENABLED`) that turns deploy jobs on.
