# M3 walkthrough: Track a job

> **Note (F1, 2026-10-20):** the screens in this walkthrough were reworked in the F1 round (file states, the Review section, the Status and Audit tabs, the status words). What the milestone built still holds; for the screens as they are now, read `docs/walkthrough/F1.md`.

## 1. The big picture

After M2, a person could send files and then had no way to see what happened. M3 adds the **Status** screen. It shows every distribution you sent (and, in **My teams**, the ones other people sent to your teams), the counts for each, and one row per delivery with its reason when it failed. The counts and rows move on their own while a distribution runs, so nobody has to refresh.

Three ideas hold it together:

- **Who may see what is decided on the server, in every query.** The sender sees all deliveries. Anyone else sees only the deliveries to a team they belong to, and counts that cover only those. A person who may not see a distribution gets the same "not found" as for an id that does not exist, so ids reveal nothing.
- **Live updates are a hint, the database is the truth.** A WebSocket connection pushes changes as they happen. But a push can be late, early or lost, so the page subscribes first, then fetches, ignores any push older than what it already shows, and fetches again once after every reconnect.
- **The server works out status; it is never stored.** A distribution is Pending, In progress, Completed, Completed with errors or Cancelled, worked out from the counts each time. So the chip cannot disagree with the numbers.

M3 adds no new table. It reads the `jobs`, `tasks`, `ws_connections` and audit tables from M1 and M2. It adds one new AWS piece: a second API Gateway of type **WebSocket**, with one Lambda (`ws`) behind it.

## 2. One distribution, watched from start to finish

Priya sends 100 files to 11 folders. That is 1,100 deliveries. She is on the Status page.

**Step 1. The page opens its live connection.** As soon as someone is signed in, the browser connects to the WebSocket address with the access token in the address. The `ws` Lambda's `$connect` route checks the token (no token, a bad token or a service token gets 401) and stores a row in `ws_connections` with the token's expiry.
- Why: browsers cannot set headers on a WebSocket handshake, so the token goes in the query. The row is how the server knows who is connected.
- Code: `workers/ws/src/handler.ts`. Test: `tests/integration/ws.test.ts` "$connect and $disconnect".
- AWS (while dev is up): API Gateway → `docbeam-dev-ws` → routes `$connect`, `subscribe`, `$disconnect`; CloudWatch → `/aws/lambda/docbeam-dev-ws`.

**Step 2. She opens the distribution.** The page sends `subscribe` with the job id and **waits for `subscribed`** before it fetches anything. The Lambda checks that she may see the job, then records the job and her teams on her connection row.
- Why: if the page fetched first and subscribed later, an update in between would fall through the gap.
- Code: `web/src/tracking/useJob.ts`, `web/src/live/socket.ts`. Test: `socket.test.ts`, `StatusPage.test.tsx` "does not fetch until the live connection has answered".

**Step 3. The page fetches.** `GET /jobs/:id` returns the counts, the chip, the folders, and what the sender's buttons may do. `GET /jobs/:id/tasks` returns 100 rows at a time as she scrolls. The table draws only the rows in view, so 2,000 rows cost the same as 20.
- Code: `services/docbeam-api/src/routes/jobs-read.ts`, `web/src/components/TaskTable.tsx`.

**Step 4. Deliveries finish and the page moves.** Each time the Delivery Lambda finishes a task it saves the result, then posts a `task_update` to every open connection for that job. A team member's connection gets counts for their teams only. The page changes the row and the numbers at once, and reads the detail again a moment later once pushes go quiet.
- Why: the push carries counts so the page need not refetch for every delivery.
- Code: `packages/shared/src/push.ts`. Test: `ws.test.ts` "pushes". On dev a real run sent 417 frames in 12 seconds.

**Step 5. She cancels.** `POST /jobs/:id/cancel` marks every still-waiting delivery as failed with the code `CANCELLED`, in one transaction under the job's lock. Deliveries already running finish. Messages still in the queue are dropped when a worker tries to claim them. The job reads **Cancelled** once nothing is open, and the API pushes one `job_update`.
- On the screen, these deliveries are **Cancelled** (grey), not Failed. They are stored as failed, but the API counts them separately (D-M3-17).
- Code: `jobs-actions.ts`, `packages/shared/src/task-outcome.ts`. Test: `tests/integration/tracking.test.ts` "POST /jobs/:id/cancel while deliveries run".

**Step 6. The connection drops.** The page reconnects with a growing delay, subscribes again, and fetches once. After every token refresh it reconnects on purpose, because the server checks a person's teams only at connect and subscribe, so someone removed from a team stops seeing updates within 15 minutes.
- Test: `socket.test.ts`; Playwright "the live connection drops mid-run and the page catches up without a reload".

## 3. The parts where a mistake would cause real harm

**A. Team visibility.** A mistake here shows a clinical team's deliveries to the wrong person. Every read route, the push and the audit all filter by the caller's teams inside the query. An outsider's answer is identical to "does not exist".
- Tests: `tracking.test.ts` "GET /jobs, /jobs/:id…" and "GET /audit is scoped…" (Raj sees Cardio only; Sam sees nothing, with the same error as a missing job); `ws.test.ts` "subscribe" and "pushes" (a task for Oncology reaches Priya, not Raj); Playwright team-viewer test; the person's two-browser check on dev.

**B. Cancel and retry.** Cancel must stop only what has not started, and never lose a running delivery. Retry must only repeat failures a retry can fix (retries used up, a failed fan-out), within 24 hours and while files are under 2 days old, and never for a cancelled job.
- Tests: the cancel test above; "POST /jobs/:id/retry" (only the right codes reset; window closed; nothing to retry; the tasks run again); on dev a cancel at 443 delivered left 793 cancelled and nothing delivered afterwards.

**C. Catch-up.** A page that shows old numbers as if they were new is worse than a slow page. The rules: subscribe, then fetch; ignore a push older than what is shown; fetch again once after every reconnect.
- Tests: `apply.test.ts`, `TaskTable.test.tsx` "ignores a push that is older than the row", Playwright "counts and rows change live, and a reload mid-run loses nothing".

**D. The teardown script.** It deletes everything in two buckets. It refuses prod, any bucket whose name is not `docbeam-dev-…-<account id>`, and the Terraform state bucket.
- Test: `tests/scripts/empty-dev-buckets.test.ts`. It ran for real on dev: 1,006 and 8,174 versions, then `terraform destroy`, nothing left behind.

## 5. Questions a reviewer might ask

1. **Why push over a WebSocket, not poll?** A distribution can change many times a second, and polling would repeat the same expensive count query. The list still polls every 30 seconds, since it only needs rough counts.
2. **What if a push is lost?** The next fetch (after a reconnect, or a quiet moment after any push) reads the truth. Pushes only make the page faster.
3. **Why subscribe before fetching?** So no update can fall between the two.
4. **How does a team member see only their deliveries?** The API gets the person's teams from the platform (cached 60 seconds) and puts them in every query. The WebSocket stores the teams on the connection at subscribe time.
5. **What if someone leaves a team?** Their open connection keeps the old teams for at most 15 minutes, until the token refresh makes a new connection.
6. **Why is a cancelled delivery stored as failed?** It reuses the existing status and audit paths. The API turns the code `CANCELLED` into its own count, so the screen never shows it as a failure.
7. **Why is Retry missing on a cancelled distribution?** Nothing failed, so there is nothing to retry. A note explains it.
8. **Why do Preview and Download exist but do nothing?** They arrive in M4 (team-scoped download). They are shown, off, with the reason.
9. **Why does the WebSocket stage have no access log?** API Gateway needs an account-wide CloudWatch role for that, which is a bigger change than it is worth. The `ws` Lambda logs every event (D-M3-15).
10. **What did the real AWS round find that tests did not?** A WebSocket stage cannot log without that account role; a made-up connection id gets 400, not 410, so a real closed connection is needed to test the cleanup; an old distribution id left in the address bar showed "not found" for the next person; and cancelled deliveries were counted as failed. All are fixed and tested.

## 6. Glossary

- **Distribution (job):** one Send. **Delivery (task):** one file to one folder.
- **Counts:** Delivered, Failed, In progress, Waiting, and Cancelled when something was cancelled.
- **WebSocket:** a long-lived connection the server can push messages through.
- **`task_update` / `job_update`:** the two push messages. The first carries one delivery and the counts; the second carries counts only, after a cancel or retry.
- **Subscribe:** telling the server which distribution this connection watches.
- **Catch-up:** subscribe, fetch, ignore older pushes, and fetch again after a reconnect.
- **410 Gone:** what API Gateway answers when a push goes to a connection that has closed. The sender removes that row.
- **Virtualized table:** a table that draws only the rows you can see.
- **Idempotent:** safe to repeat. Retry and the queue messages rely on it.
