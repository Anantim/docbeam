# M5 walkthrough: Hardening and end-to-end checks

## 1. The big picture

M0 to M4 built DocBeam and proved each piece on a small scale, mostly on Docker Compose with LocalStack. M5 asks a different question: **does the real system, on AWS, keep the promises of the blueprint when things go wrong or get big?** It adds almost no features. It adds proof, and it fixes what the proof found.

Four things hold it together:

- **Every check is a script you can run again** (`scripts/m5-*.sh`). Each prints PASS or FAIL lines with numbers, and the numbers come from the server side where possible: the API Gateway access log, CloudWatch metrics, the databases themselves. The laptop's own stopwatch is only a second opinion.
- **Dev is built from nothing with a written runbook** (`docs/RUNBOOK-first-bring-up.md`). If the runbook is wrong, the bring-up fails, so the runbook is tested every time it is used.
- **Things break on purpose.** Stop the platform for five minutes. Fail over the database in the middle of 2,000 deliveries. Delete a file after it was submitted. Drop a job message. Take the browser offline.
- **Nothing is called done without evidence.** `docs/testing/M5-RESULTS.md` has a YES or NO for every line, with the output. One NO fails the milestone, and one did on the first run: submit speed (check 5.1). It is YES now only because the requirement was changed by the person (D-M5-17): under 500 ms in normal operation, under 1 s under peak delivery load, with the worst of seven loaded runs at 992 ms.

Also in M5: the database connection now checks the certificate chain (before, it was encrypted but did not check who it talked to), a POST with no body now works from any client, and the repository was checked for secrets, keys and real email addresses before it can be made public.

## 2. One check, start to finish: the database failover (check 5.8)

`scripts/m5-failover.sh --yes` runs `scripts/m5/checks.ts failover`.

**Step 1. Switch the database to Multi-AZ.** `terraform apply -target=module.rds -var db_multi_az=true`. RDS builds a standby copy in the other zone. (Files: `infra/envs/dev/variables.tf`, `main.tf`.) In the Console (Sydney, read only): RDS, `docbeam-dev-postgres`, Configuration: Multi-AZ yes.

**Step 2. Start a long run.** 100 files of 1 MiB, sent to 20 folders: 2,000 deliveries that take minutes, not seconds. (With tiny files the whole run was over in 20 seconds and the first two attempts missed the point.)

**Step 3. Fail over.** When 100 are delivered, `aws rds reboot-db-instance --force-failover`. The standby becomes the primary: 16:20:53 to 16:21:13, 20 seconds. For about 15 seconds nothing can reach the database.

**Step 4. Watch the system heal itself.** Delivery copies fail on the database and put each message back with a retry gap (30 seconds, then 2, 5 and 10 minutes). The Platform returns 500 for 15 seconds. When the database is back, the retries succeed.

**Step 5. Prove nothing was lost, from the databases.** In the DocBeam database: 2,000 tasks, all completed, none RETRIES_EXHAUSTED. In the Platform database: 2,000 documents with 2,000 different `source_task_id` (each task stored once). In CloudWatch: Task DLQ and Job DLQ at 0 for the whole window.

**Step 6. Switch back to Single-AZ**, always, even if the check fails (a `finally` block).

The first time this ran, step 4 did **not** heal. The Platform answered 500 for more than ten minutes and 853 of 2,000 tasks ended RETRIES_EXHAUSTED. Its two pooled database connections pointed at the old primary and never reported an error, so every query waited for ever. That is the finding of the milestone (D-M5-13). The fix is two settings (a 20-second query timeout and TCP keep-alive), and the same drill then recovered in 15 seconds.

## 3. The parts where a mistake would cause real harm, and the tests that cover them

**1. The database connection settings** (`packages/shared/src/db.ts`, `db-url.ts`). Without a query timeout, one failover can block a service for good while its health check still says "ok". Without the certificate check, anyone inside the network could pretend to be the database. Tests: `db.test.ts` (every pool has a timeout and keep-alive), `db-url.test.ts` (the URL checks the chain, and refuses to build without the bundle), and on dev the failover drill and `tls.txt` (a wrong bundle fails, a missing one refuses to start).

**2. Who can see a file** (checks 5.7, 5.9, 5.12). A file sent only to Oncology must be invisible to Raj, who is in Cardio: 404 for the job, 404 for the download link, nothing in his audit trail. An infected file must be gone and never downloadable. Tests: `m5-team-viewer.sh`, `m5-eicar.sh`, `m5-security.sh`; locally `downloads.test.ts` and `jobs.test.ts`.

**3. Exactly one document per delivery** (checks 5.2, 5.3, 5.8). Messages can arrive twice and Lambdas can die half way. The Platform keeps one document per task id. The checks count documents and distinct task ids in the database.

**4. What the sender is told when a delivery cannot happen** (checks 5.2, 5.4). A removed member's 100 deliveries must read NOT_AUTHORIZED_AT_DELIVERY and the other 1,900 must complete; a deleted file must read FILE_NOT_UPLOADED at once. The second one failed on AWS (S3 answers 403 instead of 404 when the caller cannot list the bucket) and is why the Delivery role now has `s3:ListBucket` (D-M5-8).

## 4. What can be ignored

- The CSS and screenshots in `docs/testing/m5-evidence/` except as proof.
- The failed first versions of checks in `m5-evidence/*-run1.txt`: they show what was wrong with the checks, and one of them shows the bug that the failover drill found.
- `scripts/m5/lib.ts` details (retries of dropped connections, token renewal). Read `scripts/m5/checks.ts` only for what each check asserts.

## 5. Questions a reviewer might ask

1. **Why was M5 a fail, and why is it a pass now?** Check 5.1: the 100 x 20 submissions took 0.35 to 1.6 seconds under delivery load, so p99 was 808 ms against a target of 500; the median is 30 ms. One cause was found and fixed (10,000 bound parameters in one insert). A second bring-up timed every phase of the request: the parse, the schema, the token check and the connection pool are not the problem; with Delivery paused the p99 is 225 ms; under load the time goes into small database queries while up to 49 Delivery copies queue on one job's row lock on a small database. The person then changed the requirement (D-M5-17): 500 ms in normal operation, 1 s under peak load. All seven loaded runs are under 1 s, the worst by only 8 ms. That is a pass by a thin margin and a known limit, not a clean pass.
2. **Why measure latency at the gateway and not from the laptop?** The laptop adds the internet. The gateway's `responseLatency` is the time from the request arriving to the answer leaving.
3. **Why 1 MiB files in the outage and failover checks?** With 4 KB files 2,000 deliveries finish in 20 seconds, before the platform can be stopped. The checks now assert that the stop landed in the middle of the run.
4. **Why wait two minutes after pausing a trigger?** On dev, six deliveries ran about a minute after the mapping said Disabled. The checks wait, and first assert that every task is still pending.
5. **Is a 523-second pause after the failover a problem?** It is the quiet tail, not a stop: 1,992 of 2,000 were done within 90 seconds. The stragglers followed the retry gaps, and one message waited the queue's 12-minute visibility timeout. Nothing was lost (`failover.txt`).
6. **Why does the Delivery Lambda have 3,008 MB?** A 1 GiB file used all of 1,024 MB and timed out. With 3,008 MB it took 37 seconds.
7. **Could this have been caught on Compose?** None of the seven findings could: Compose Postgres never fails over, LocalStack answers 404 for a missing object, test jobs have 4 tasks, and the files are small.
8. **Why is the older author email still in the history?** Rewriting 127 commits would change every SHA and break links. It is the author's own address, not a leaked secret; a `.mailmap` maps it (D-M5-2).
9. **Was prod touched?** Never. It stays as code, and a first prod bring-up would need the runbook's section 9.
10. **What stays up after M5?** Nothing: dev is torn down after the demo recording (`docs/STATUS.md` says when). The demo video is `docs/demo/docbeam-demo.mp4` (recorded by the person in OBS); `docs/DEMO-SCRIPT.md` is the plan.

## 6. Glossary

- **p99:** the time that 99 of 100 requests beat. With 100 requests it is nearly the slowest one.
- **Failover:** a Multi-AZ database switches to its standby copy when the primary fails or is rebooted.
- **Visibility timeout:** how long SQS hides a message after a worker takes it. If the worker does not delete it or set a new gap, the message returns after this time (720 s for the task queue).
- **Retry gap:** the wait before a failed delivery is tried again: 30 s, 2, 5, 10 minutes.
- **DLQ:** dead-letter queue, where a message goes after too many failed tries. The checks require it to stay empty.
- **verify-full:** a Postgres TLS mode that checks the certificate chain and the host name.
- **Stop rule:** in an unattended run, a problem that fails twice is recorded as a NO and skipped.
