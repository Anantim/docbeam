# F1 walkthrough: the reviewer's feedback round

## 1. The big picture

After M5 a reviewer used DocBeam and sent back feedback. It was not about whether the system works (it did) but about whether a coordinator who is not technical can use it at a glance. The F1 round changed how the screens look, how they are laid out, and a few rules, without changing what the system does for the upload or the deliveries.

What changed, in plain terms:

- **One look.** The stylesheet starts with a small design system: a neutral palette, one accent colour, colours for status only (green, amber, red, blue, grey), five text sizes, one spacing scale, one corner radius, one shadow. Every rule after it uses those values. A delivery, a distribution and a file being uploaded use the same status chip.
- **Distribute is two columns.** Files on the left, destinations on the right, one bar at the bottom. You can tick folders before adding files: a folder ticked for all files stays ticked for every file added later. Only folders are destinations; binders are headings. Send is the one filled button and asks one question first ("Send 3 files to 5 folders?", "Delivered files can't be recalled", Cancel is the default).
- **Status shows job history only.** A list of distributions (Mine, My teams, All I can see, and a status filter) and a side panel for the one you open: its deliveries with Retry failed and Cancel distribution. The address keeps the panel open. There is no audit view in the page any more (D-F1-13).
- **Big lists are paged.** The destination tree loads 20 rows when you open a level and the next 20 when you scroll to the end. So does the list of distributions.
- **Every screen got the same care:** the same words (Pending, In progress, Completed, Failed, Cancelled), keyboard use, dialogs that keep the focus inside, skeleton rows while loading, one icon style, one font, and screens that work down to 1024 px.

## 2. One thing, start to finish: opening a folder of 60 children

1. A coordinator opens the Destinations tree. Only the teams load (`GET /teams`, 20 rows at most). Nothing below is loaded yet.
2. They open a team, a binder and a folder. Each click asks for one level: `GET /folders/<id>/contents` with no query, so the first 20 children (`web/src/components/Destinations.tsx`).
3. The server answers 20 folders and a `nextCursor`, a code that says "after Batch 020" (`services/platform/src/routes/browse.ts`, `paging.ts`). It first checks that the caller is in the team that owns the folder; a stranger gets the same "not found" on every page.
4. When the "more" row at the end of the list scrolls into view, the browser asks again with `?cursor=…` and gets the next 20. After the third page `nextCursor` is empty and the row disappears.
5. In the AWS Console nothing special shows: it is three plain requests to the same API Gateway route (CloudWatch, the gateway access log).

## 3. The parts where a mistake would cause real harm

- **Access across pages.** A cursor is just a position; the access check runs before every page. Tests: `tests/integration/platform.test.ts` ("pages a folder of 60 children… the same access rule on every page"), `browse-paging.spec.ts`.
- **The status filter.** `GET /jobs?status=` works out the status in the database from the deliveries the caller may see, so a team member never sees a status or a count that includes another team's deliveries. Tests: `tests/integration/tracking.test.ts` (same job "in progress" for the sender, "completed with errors" for a team member).
- **The question before Send.** A distribution cannot be recalled. The dialog starts with Cancel focused, so Esc, Enter and a click outside all answer no; Tab cannot leave it (`useFocusTrap`). Tests: `Distribute.test.tsx`, `m2.spec.ts`.
- **A folder ticked early.** The tick must reach every file added while it stays ticked, and stop when it is unticked. Tests: `mapping.test.ts` (`applyHeld`), `Distribute.test.tsx`.

## 4. What can be ignored

The colour tokens' exact values, the memo comparators that stop rows redrawing, and the details of the container queries that shrink the panel. They matter for speed and tidiness, not for what the system promises.

## 5. Questions a reviewer might ask

1. **Why not a UI library?** The design is small and the rules are strict (one accent, status colours only). Plain CSS variables kept every value in one place; a library would have added a second place.
2. **Why are binders not destinations?** The feedback said the tree offered a choice coordinators never use. Only folders receive files, which also removes a class of mistakes.
3. **Why does a ticked folder stay ticked for files added later?** Coordinators work in either order. Ticking first and adding files second used to lose the tick after the first batch.
4. **Why a cursor instead of page numbers?** A page number breaks when rows are added while you scroll (a repeat or a gap). A cursor names the last row seen, so it cannot.
5. **Where did the Audit trail go?** Out of the page (D-F1-13). The backend still writes every audit record and `GET /audit` still answers; nothing in the web app calls it. A file refused by the malware scan shows only in the Distribute file list. The old addresses open the first screen.
6. **How do you know the screens are faster?** Two tests count renders: ticking one of 40 folders used to draw all 40 rows and now draws one; a 30-second refresh of 40 distributions with nothing changed drew 40 rows and now draws none.
7. **What did you not do?** The destination search only looks at rows that were loaded; real search over every folder needs a server-side search. It is listed in `docs/STATUS.md`.
8. **What does the dev run prove that tests do not?** The same checks on AWS: the browse timing for the 50-team user, a 2,000-delivery submit in under 500 ms (quiet) and under 1 s (loaded), and the changed screens in a real browser against the deployed system.

## 6. Glossary

- **Cursor:** a code that says where the last page ended; the server finds the rows after it.
- **Keyset paging:** paging by "rows after this one" instead of "page N".
- **Token (design):** a named value, such as `--accent`, used everywhere instead of a raw colour.
- **Status chip:** the small label with a dot (Pending, In progress, Completed, Failed, Cancelled).
- **Side panel:** the box on the right of Status that shows one distribution.
- **Focus trap:** keeps the Tab key inside an open dialog.
- **Skeleton:** grey placeholder rows shown while a list loads.
